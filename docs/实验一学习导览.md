## 0. 先抓住一句话（1 分钟）

MapReduce 把“大规模数据处理”拆成两个用户函数：Map 把输入变成中间键值对，Reduce 把同一个 Key 的所有 Value 聚合成结果。系统负责的是**在哪台机器上执行、输入怎么切、结果怎么分区、失败怎么办**。本实验实现的是后半部分：一个 Coordinator 调度多个 Worker，用共享文件系统完成 Shuffle。

## 1. 用 Word Count 理解数据流（4 分钟）

假设输入只有一行：

```text
a b a
```

应用提供的 Map 函数会被调用一次，产生：

```text
(a, "1")  (b, "1")  (a, "1")
```

系统用 `hash(key) % nReduce` 决定每个键值对去哪个 Reduce 分区。本实验 `nReduce=10`，所以每个 Map 任务会写出 `mr-X-0` 到 `mr-X-9` 十个中间文件。

编号为 Y 的 Reduce 任务读取所有 Map 的 `mr-X-Y`，按 Key 排序后得到：

```text
a: ["1", "1"]
b: ["1"]
```

再调用应用的 Reduce 函数：Word Count 返回值的数量，于是输出 `a 2`、`b 1`。把所有 `mr-out-*` 合并，就得到最终结果。

对整个作业而言，真正重要的是三件事：

1. **输入可以独立切分**：每个文件对应一个 Map 任务。
2. **中间数据按 Key 分区**：相同 Key 必须到同一个 Reduce，否则 `a` 会被统计成两份。
3. **Reduce 必须等所有 Map 完成**：少读任何一个 Map 的输出，结果都会错。

## 2. 为什么需要 Coordinator 和 Worker（3 分钟）

如果把所有逻辑写在一个程序里，就是 `mrsequential.go`：简单、正确，但只能串行。要并行，就必须有人回答“下一步做什么”：

- **Coordinator** 是控制面：保存任务表、任务状态、当前阶段，分配任务，处理超时。它不读取大文件，也不搬运中间数据。
- **Worker** 是数据面：拉取任务，调用应用 Map/Reduce 函数，读写共享目录中的文件。
- **共享文件系统** 是数据交换层：Map 写 `mr-X-Y`，Reduce 读 `mr-X-Y`，Coordinator 完全不必转发数据。

对应到 [coordinator.go](../Exp1-MapReduce/mit-lab/src/mr/coordinator.go) 和 [worker.go](../Exp1-MapReduce/mit-lab/src/mr/worker.go)，一个作业的生命周期是：

```text
phaseMap ── 全部 Map 完成 ──> phaseReduce ── 全部 Reduce 完成 ──> phaseDone
```

Coordinator 的 `Done()` 只回答一个问题：是否已经进入 `phaseDone`。`main/mrcoordinator.go` 每秒轮询一次，进入 Done 就退出。

## 3. RPC 在这套系统里承担什么（3 分钟）

Worker 与 Coordinator 是不同进程，不能直接调用对方的函数，因此用 [rpc.go](../Exp1-MapReduce/mit-lab/src/mr/rpc.go) 定义协议。本实验只有两个核心 RPC：

| RPC | 方向 | 作用 |
|---|---|---|
| `GetTask` | Worker → Coordinator | 申请下一个 Map/Reduce 任务；可能得到 `TaskWait` 或 `TaskExit` |
| `ReportTask` | Worker → Coordinator | 报告任务成功/失败，并带回 `Attempt` 版本号 |

Coordinator 用 `rpc.Register(c)` 和 `rpc.HandleHTTP()` 注册服务，通过 Unix domain socket 监听；Worker 用 `rpc.DialHTTP("unix", sockname)` 建立连接。Go 的 `net/rpc` 只会序列化**首字母大写**的字段，所以 RPC 结构体中的 `TaskID`、`Attempt`、`InputFile` 等字段必须导出。每次调用都用新构造的空 reply，也是一个容易踩的坑。

可以把它类比为 C++ 的远程函数调用：参数和返回值被序列化后走 socket，只是 Go 把注册、编码和网络细节封装得更轻量。

## 5. 从 C++/Python 看本实验用到的 Go（3 分钟）

| 概念 | C++/Python 直觉 | 本实验中的位置 |
|---|---|---|
| `struct` + 方法 | 类似只有数据成员的 class；Go 没有继承 | `Coordinator`、`taskInfo` |
| 指针接收者 | 类似 C++ 的 `this`，但显式写成 `func (c *Coordinator)` | `GetTask`、`ReportTask` |
| `:=` 与多返回值 | Python 解包；Go 把 `value, err` 作为惯例 | `reply, ok := requestTask(...)` |
| 错误处理 | 没有异常，用 `if err != nil` 向上返回 | 文件读写、JSON 编解码 |
| `defer` | 类似 RAII/`try/finally`，在函数返回时执行 | `defer c.mu.Unlock()`、文件清理 |
| 切片 `[]T` | 比 `vector` 更轻，带长度和容量视图 | `[]KeyValue`、`[]string` |
| `map` | `dict`/`unordered_map`；但并发读写需要额外加锁 | 插件内部有使用，Coordinator 不用 map |
| goroutine | 比线程轻；由 Go runtime 调度 | `net/rpc` 为每个请求启动处理 |
| `sync.Mutex` | 类似 `std::mutex` | 保护 Coordinator 的全部共享字段 |
| `plugin.Open` | 类似 `dlopen`，但只用 Go 插件机制 | `main/mrworker.go` 加载 `wc.so` |
| 大写导出 | 类似 Python 的“公开命名”约定，但 Go 由编译器强制 | RPC 字段、跨包函数 |

一个容易忽略的语法点是：Go 的变量声明后会自动得到零值（`0`、`""`、`nil`、`false`）。Coordinator 中 `taskIdle` 恰好是 iota 的零值，所以初始化任务时不需要显式写 `status: taskIdle`。

## 6. 五个机制，必须能自己讲清（5 分钟）

### 6.1 `sync.Mutex` 保护的是什么

保护的是“读—判断—修改”这一整段原子性，例如：

```go
c.mu.Lock()
defer c.mu.Unlock()
if task.status != taskRunning || task.attempt != args.Attempt {
    return nil
}
task.status = taskCompleted
```

如果只锁“写”而不锁“判断”，两个 goroutine 可能都看到任务仍在运行，然后都做决定。锁不包住文件 I/O，也不包住 Map/Reduce 函数，因此不会把并行计算串行化。

### 6.2 任务状态机

每个任务只会经历 `Idle → Running → Completed`。Worker 本地失败时回到 `Idle`；超时重派时仍是 `Running`，但 `Attempt` 增加。旧 Worker 的完成报告会因为 `Attempt` 不匹配而被丢弃。

### 6.3 10 秒超时

`taskTimeout = 10 * time.Second`。Coordinator 不启动额外的超时 goroutine，而是在 Worker 来 `GetTask` 时顺便检查运行时间是否超过 10 秒。这个实现简单，但意味着“必须有 Worker 持续请求”才会触发重派；报告的限制章节也提到了这一点。

### 6.4 文件分区与 Shuffle

Map 端对每个 Key 计算 `ihash(k) % nReduce`，写到 `mr-X-Y`；Reduce Y 只读所有 X 的 `mr-X-Y`。这里没有中心化的 Shuffle 服务，分区本身就是 Shuffle 协议。哈希必须是确定性的，否则同一个 Key 会被不同 Map 写到不同 Reduce。

### 6.5 临时文件与原子重命名

```text
创建 .mr-map-X-Y-* 临时文件
→ 写入 JSON
→ Flush / Sync / Close
→ os.Rename 为 mr-X-Y
```

`rename` 在同一个文件系统内是原子的。读者要么看到完整的旧文件，要么看到完整的新文件，不会看到写了一半的 JSON。Reduce 的 `mr-out-X` 使用同样的策略。注意：这保证单个文件内容完整，不提供跨多个文件的事务；本实验依靠“任务完成报告”控制可见性。

## 7. 五个核心知识点（带走即可）

1. **控制面与数据面分离**：Coordinator 只调度，Worker 和共享文件系统处理数据。
2. **确定性分区 + 阶段屏障**：相同 Key 到同一个 Reduce，Reduce 必须等全部 Map。
3. **超时是失败检测的近似**：必然可能重复执行，因此需要 `Attempt`。
4. **至少一次执行 + 原子提交**：重复执行可以接受，前提是输出完整且对这些应用幂等。
5. **临界区尽量短**：锁任务状态，不锁 Map/Reduce 和文件 I/O。

## 8. 自检问题（含参考答案）

**Q1：只有 `TaskID` 不够吗，为什么还需要 `Attempt`？**

不够。超时重派时任务编号不变，如果旧 Worker 和新 Worker 都报告成功，Coordinator 无法区分谁属于当前这次执行。`Attempt` 是 fencing token，能拒绝旧执行的迟到报告。

**Q2：如果允许 Reduce 在 Map 尚未全部完成时启动，会发生什么？**

Reduce Y 需要读取所有 `mr-X-Y`。提前启动会漏掉尚未产出的 Map 输出，导致某些 Key 的 Value 变少，结果错误。因此必须有 Map→Reduce 的阶段屏障。

**Q3：为什么不能把 Map/Reduce 函数也放进 `c.mu` 的临界区？**

Map/Reduce 可能读写大量文件、执行数秒。把锁持有到函数结束会让所有 RPC 被串行化，Worker 无法并行，甚至可能因为长时间等待导致超时重派。正确做法是只在锁内操作元数据。

**Q4：为什么不能直接 `os.Create("mr-X-Y")` 后慢慢写？**

Worker 可能在写到一半时崩溃，Reduce 会读到不完整的 JSON；最终输出也可能出现半截文件。临时文件写完、落盘后再 `os.Rename`，可以让正式文件只在完整时出现。

**Q5：重复执行一个 Map 任务，为什么最终结果通常不会重复？**

重派会覆盖同一个 `mr-X-Y`，而不是追加；Reduce 按 Key 重新分组，最终覆盖 `mr-out-X`。测试应用对同一输入的输出是确定性的，因此重复执行得到相同内容。如果应用函数本身非确定，仍需更严格的提交协议，这也是报告“局限与改进方向”中的内容。
